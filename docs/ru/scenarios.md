# Сценарии использования

> English version: [docs/en/scenarios.md](../en/scenarios.md).

Зачем нужен lexicon, по задачам: что решает каждый сценарий, какими
вызовами и с каким работающим примером. Справочник по всем упомянутым
вызовам — [library.md](library.md) и [cli.md](cli.md); эта страница
отвечает на вопросы «зачем» и «что выбрать».

У каждого сценария указана версия, с которой он доступен. Ещё три пометки
ведут мини-changelog прямо рядом с возможностью:

- **Поведение в 0.1.0** — правило, принятое осознанным решением и способное
  измениться. Когда оно изменится, строка переедет в **Историю**.
- **История** — что поменялось в следующих версиях; выдержка из
  [CHANGELOG.md](../../CHANGELOG.md) по конкретной возможности (источник
  истины — CHANGELOG).
- **⚠ переиндексация** — изменение меняет формы или термы: поднимается
  `textnorm.Rules.Version` или версия анализатора, меняется
  `Analyzer.Version()`, и хосту нужно пересобрать производные данные (см.
  [сценарий 13](#13-понять-когда-переиндексировать)).

Примеры: `go run ./examples/<name>` из корня репозитория
([examples/](../../examples/README.md)); функции `ExampleXxx` — в
`example_test.go` и `textnorm/example_test.go`, они отображаются на
pkg.go.dev. Все примеры, кроме `base`, работают без скачивания: словари в
них — крошечные TSV, заданные в коде.

## 1. Сравнивать слова независимо от орфографии

**Задача.** Чтобы «Вѣра», «Вера» и «ВЕРА», «Ѳеодоръ» и «Федор», «ёлка» и
«елка» совпадали — в поисковом индексе, при дедупликации, при сопоставлении
запроса со старыми документами.

**Как.** Выбрать набор правил: `textnorm.Modern` (нижний регистр, NFC,
ё→е, диакритика удаляется, кроме й) или `textnorm.PreReform` (Modern плюс
ѣ→е, і→и, ѳ→ф, ѵ→и и другие старые буквы, и конечный ъ, удаляемый в каждой
части слова через дефис). `textnorm.NormalizeWord(r, w)` — форма, по
которой слово индексируется и сравнивается; `textnorm.Orthography(r, s)`
приводит целую строку (конечный ъ — правило слова, он остаётся). Результат
годится только для сравнения; смещения на него никогда не указывают
([сценарий 3](#3-токены-со-смещениями-в-исходный-текст)).

```go
textnorm.NormalizeWord(textnorm.PreReform, "Санктъ-Петербургъ") // санкт-петербург
textnorm.NormalizeWord(textnorm.Modern, "Ёлка")                 // елка
```

Свой набор правил — это новое значение `textnorm.Rules` со своими `Name` и
`Version`; `Modern`/`PreReform` менять нельзя.

**Пример:** [orthography](../../examples/orthography/main.go),
`ExampleNormalizeWord`, `ExampleOrthography`; CLI `analyze --ortho
prereform`.

**Доступно с:** 0.1.0 (`Modern` и `PreReform` с `Version` "3").

## 2. Исправить латиницу внутри кириллических слов

**Задача.** В выходе OCR и в набранном вручную тексте в кириллические
слова попадают похожие латинские буквы: «Kот», «Iоаннъ». Такое слово
никогда не совпадёт со своей словарной формой.

**Как.** Вызывать ничего не нужно: это делает `Rules.Homoglyphs` в
токенизаторе и в `Orthography`. Часть слова (части разделяются дефисами),
в которой есть кириллическая буква и нет других букв, кроме известных
гомоглифов, считается кириллической: токенизатор оставляет её одним словом
`ScriptCyrillic`, а гомоглифы заменяются. Части с другими латинскими
буквами («Kотw») или без кириллицы («XIX») не трогаются. `PreReform` также
считает латинские i/I дореформенными і/І.

**Пример:** [orthography](../../examples/orthography/main.go) («Kот»,
«Iоаннъ», «XIX»).

**Доступно с:** 0.1.0. Буквы с диакритикой (латинская буква с ударением
внутри кириллического слова) тоже приводятся.

## 3. Токены со смещениями в исходный текст

**Задача.** Подсветить найденное слово, подчеркнуть сущность или вырезать
цитату из текста ровно в том виде, как он хранится, — хотя сопоставление
шло по нормализованной форме, и даже если клиент на JavaScript (строки
UTF-16).

**Как.** `textnorm.Tokenize(r, input)` возвращает все токены — слова любой
письменности, числа, пунктуацию, символы — с байтовыми смещениями
(`Start`/`End`, всегда `input[Start:End] == Raw`) и смещениями в кодовых
точках (`RuneStart`/`RuneEnd`); границы проходят по графемным кластерам.
`textnorm.UTF16Offsets(input, offs...)` переводит байтовые смещения для
JavaScript. `textnorm.SplitHyphen(tok)` даёт части слова через дефис, у
каждой свои смещения и `Form`. `Token.Dotted` отмечает слово, за которым
сразу идёт «.» (кандидат в сокращения); `SentenceEnd` — «.», «!», «?», «;»,
«…» и последний токен перед пустой строкой.

```go
for _, t := range textnorm.Tokenize(textnorm.PreReform, input) {
    fmt.Println(input[t.Start:t.End], t.Form, t.RuneStart, t.RuneEnd)
}
```

**Пример:** [tokenize](../../examples/tokenize/main.go),
`ExampleTokenize`, `ExampleSplitHyphen`, `ExampleUTF16Offsets`.

**Доступно с:** 0.1.0.

**Поведение в 0.1.0:** смещения всегда указывают на вход ровно в том виде,
в каком он передан в `Tokenize`, и никогда — на нормализованную строку. Это
обязательный контракт, а не настройка по умолчанию: он не изменится.

## 4. Термы для поискового индекса

**Задача.** Превратить поле документа в термы индекса: «Кота», «котом» →
«кот»; служебные слова отброшены; числа сохранены; неоднозначная форма
(«стали» → «сталь», «стать») индексируется под каждой леммой.

**Как.** Открыть `Registry` ([сценарий 10](#10-свои-словари-файлы-и-встроенные)),
создать один `Analyzer` через `lexicon.NewAnalyzer(reg, rules,
AnalyzerOptions{})` и вызвать `Analyze(text, profile, lexicon.ModeIndex)`.
У каждого `Term` есть исходный `Token`, форма поиска `Form` и `Lemmas`
(`Text`, `Flags`, а также `Tag`, `Kind`, `Dict` разбора, давшего лемму).
Индексируйте леммы; `Form` тоже сохраните, если ищете по префиксу
([сценарий 5](#5-разбор-поискового-запроса-по-мере-ввода)). Слово через
дефис индексируется целиком и по частям. Индексируются только кириллические
слова и числа.

Флаги говорят, насколько лемме можно доверять: без флагов — словарное
слово; `ambiguous` — одна из нескольких лемм; `predicted` — слова нет ни в
одном словаре, лемму угадал базовый словарь по окончанию; `unknown` —
разборов нет вовсе, лемма — сама форма; `abbrev`, `reform` — см. сценарии
[9](#9-сокращения-в-записях) и [8](#8-дореформенные-тексты).

```go
a := lexicon.NewAnalyzer(reg, textnorm.Modern, lexicon.AnalyzerOptions{})
for _, t := range a.Analyze("Кота и пса стали кормить", lexicon.Profile{Name: "text"}, lexicon.ModeIndex) {
    for _, l := range t.Lemmas {
        index.Add(docID, l.Text)
    }
}
```

`Analyzer` безопасен для конкурентного использования и кэширует леммы по
имени профиля (`AnalyzerOptions.CacheSize`, по умолчанию 50 000 записей;
кэш сбрасывается при изменении набора словарей). Используйте один
`Analyzer` и для индексации, и для разбора запросов — тогда они не
разойдутся.

**Пример:** [index](../../examples/index/main.go),
`ExampleAnalyzer_Analyze`; с настоящим базовым словарём —
[base](../../examples/base/main.go).

**Доступно с:** 0.1.0.

**Поведение в 0.1.0:**
- Стоп-слово — слово, все точные разборы которого — служебные части речи
  (PREP, CONJ, PRCL, INTJ); разборы с `Abbr` не учитываются (буквенные
  «сокращения» OpenCorpora для «в», «с», «и»). Списка стоп-слов нет: у
  «что», «как», «из» есть неслужебные разборы, и они индексируются.
- Предсказания используются только если ни у формы, ни у её дореформенных
  вариантов нет точного разбора, и только из словарей вида `base`. Если
  профиль отфильтровал все точные разборы, лемма — `unknown`: догадка
  никогда не подменяет отфильтрованное словарное слово.

## 5. Разбор поискового запроса по мере ввода

**Задача.** Строка поиска: «Кузнецова Ив» должна находить документы с
«Кузнецов» в любой форме и с любым словом, начинающимся на «ив».

**Как.** `Analyzer.ParseQuery(q, profile)` разбирает запрос так же, как
`ModeIndex`. Последнее слово, если после него ничего нет (даже пробела),
становится `Query.Partial`: ищите его по префиксу среди проиндексированных
форм и по его леммам (объединение). Служебное слово в конце без лемм и
ищется только по префиксу. `Query.Terms` — законченные слова. Число или
слово с точкой в конце считаются законченными.

```go
q := a.ParseQuery("кота Кузн", name)
// q.Terms: кота → кот; q.Partial: кузн — префикс «кузн*» или его леммы
```

**Пример:** [query](../../examples/query/main.go),
`ExampleAnalyzer_ParseQuery`.

**Доступно с:** 0.1.0.

## 6. Профиль на поле против омонимии

**Задача.** В поле «имя» «Вера» — имя, а не «вера», «Мороз» — фамилия, а
не «мороз»; в поле «место» «Покровском» — село, а не прилагательное. Всё
это на одном наборе словарей.

**Как.** `Profile` — конфигурация хоста: `Name` (ключ кэша, уникален в
пределах `Analyzer`), `Kinds` (виды словарей, по которым ищем; пусто — все)
и `Grammemes` (для вида: разбор остаётся, только если в его теге есть одна
из граммем). Виды хоста (`surname`, `given`, `toponym`, …) объявляются в
`Options.Kinds`. Разборы идут в порядке реестра, лемма хранит тег первого
давшего её разбора.

```go
name := lexicon.Profile{
    Name:      "name",
    Kinds:     []lexicon.Kind{lexicon.KindBase, "surname", "given", "patronymic"},
    Grammemes: map[lexicon.Kind][]string{lexicon.KindBase: {"Name", "Surn", "Patr"}},
}
place := lexicon.Profile{
    Name:      "place",
    Kinds:     []lexicon.Kind{lexicon.KindBase, "toponym", lexicon.KindAbbrev},
    Grammemes: map[lexicon.Kind][]string{lexicon.KindBase: {"Geox"}},
}
```

CLI: `--profile 'name:base[Name|Surn|Patr],surname'`.

**Пример:** [profiles](../../examples/profiles/main.go), `ExampleProfile`.

**Доступно с:** 0.1.0.

**Поведение в 0.1.0:** профили не входят в `Analyzer.Version()`. Хост,
изменивший определение профиля, версионирует его сам и переиндексирует
поля, которые его используют.

## 7. Разметить каждый токен (вход для NER и проверки)

**Задача.** Показать текст с разметкой каждого слова — для предварительной
разметки перед проверкой человеком, для интерфейса с подсветкой или для
своих правил поиска сущностей, — не теряя пунктуацию и служебные слова,
важные для контекста.

**Как.** `Analyze(text, profile, lexicon.ModeFull)` возвращает ровно один
`Term` на токен, включая пунктуацию (у пунктуации и символов лемм нет).
Служебные слова сохраняют леммы с флагом `stop`, а не отбрасываются. Числа
и некириллические слова получают лемму `unknown` без обращения к словарю.
Смещения берутся из токена
([сценарий 3](#3-токены-со-смещениями-в-исходный-текст)).

**Пример:** [full](../../examples/full/main.go),
`ExampleAnalyzer_Analyze_full`; CLI `analyze --mode full`.

**Доступно с:** 0.1.0.

**История:** словарный NER поверх этого режима — газетиры, правила,
спаны — запланирован на 0.2 ([ниже](#запланировано-словарный-ner-правила-паттерны)).

## 8. Дореформенные тексты

**Задача.** Разбирать документы до 1918 года: «Иванъ Кузнецовъ изъ села
Покровскаго» — старые буквы, конечный ъ и окончания прилагательных -аго,
-яго, -ыя, -ія, которых нет ни в одном современном словаре.

**Как.** Создать `Analyzer` с `textnorm.PreReform` (буквы и ъ,
[сценарий 1](#1-сравнивать-слова-независимо-от-орфографии)). Для окончаний
ничего не нужно: если у формы нет точного разбора, анализатор по порядку
пробует её современные варианты из `textnorm.ReformVariants` и берёт первый,
известный словарям; лемма получает флаг `reform`, а индексируемая `Form`
остаётся как в тексте («покровскаго»).

```go
textnorm.ReformVariants("покровскаго") // [покровского]
textnorm.ReformVariants("хорошаго")    // [хорошого хорошего]: окончание зависит от ударения
```

**Пример:** [full](../../examples/full/main.go) («Шуйскаго» →
«шуйский[reform]»), `ExampleReformVariants`; CLI `analyze --ortho
prereform`.

**Доступно с:** 0.1.0.

## 9. Сокращения в записях

**Задача.** Метрические книги и ревизские сказки полны сокращений:
«кр-нин» (крестьянин), «с.» (село или сын), «у.» (уезд), «губ.»
(губерния). Индексировать и размечать их по полным словам.

**Как.** Подключить словарь вида `abbrev` — файл `abbrev.<name>.tsv` или
встроенный, — у которого в колонке словоформы стоит сокращение с точкой
или дефисом, а в колонке леммы — полное слово. Слово с точкой сначала
ищется вместе с точкой, слово через дефис — сначала целиком; лемма
получает флаг `abbrev`, а `Term.Form` включает точку («с.»). Список
сокращений lexicon не поставляет: это данные хоста.

```
крестьянин	кр-нин	NOUN
село	с.	NOUN
сын	с.	NOUN
```

**Пример:** [abbrev](../../examples/abbrev/main.go).

**Доступно с:** 0.1.0.

**Поведение в 0.1.0:**
- Однобуквенное сокращение с точкой («с.», «ц.») всегда `ambiguous`;
  однобуквенное слово без точки («с» — предлог) никогда не получает
  разбора-сокращения.
- Поиск сокращений не учитывает `Kinds` профиля: профиль без `abbrev` всё
  равно раскрывает «с.». Строгая фильтрация по профилю — открытый вопрос
  ([todo](../todo.md)).
- Без словаря сокращений решает базовый словарь: в базе OpenCorpora «г.»
  даёт «г», «кр-нин» угадывается.

## 10. Свои словари: файлы и встроенные

**Задача.** Добавить словарь хоста — фамилии, имена, топонимы, сословия —
в виде словарей, которые пользователи могут править, а часть поставлять
внутри бинарника.

**Как.** `lexicon.Open(ctx, lexicon.Options{...})`:
- `Dir` — каталог с файлами `<kind>.<name>.dat` (бинарный формат gomorphy,
  отображается в память) и `<kind>.<name>.tsv`
  (`lemma<TAB>wordform[<TAB>tags]`, собирается при загрузке через
  `ImportTSV` из gomorphy). Имя словаря — имя файла без расширения.
  Символические ссылки разыменовываются.
- `<file>.meta` — необязательный файл происхождения из строк
  `key: value` (`source`, `license`, `version`, `url`, `generated_from`),
  доступен как `Entry.Manifest`.
- `Builtin` — словари хоста в памяти (`//go:embed`), `FormatTSV` или
  `FormatDat`. Файл с тем же именем в `Dir` заменяет встроенный словарь,
  так что пользователи могут переопределить поставляемые данные без
  пересборки.
- `Kinds` — собственные виды хоста. Файл необъявленного вида (опечатка
  вроде `surnme.x.tsv`) виден в списке с ошибкой и не используется; nil
  принимает любой допустимый вид (так делает CLI).

Порядок реестра: базовый словарь, затем встроенные по порядку, затем
остальные файлы по имени. Испорченный файл никогда не ломает `Open`:
`Registry.List()` показывает его с `Entry.Error`, `Registry.Summary()`
учитывает его.

**Пример:** [registry](../../examples/registry/main.go),
[embed](../../examples/embed/main.go), `ExampleOpen`; CLI `dicts list`.

**Доступно с:** 0.1.0.

**Поведение в 0.1.0:** предсказания дают только словари вида `base`.
gomorphy строит предсказание для любого собранного словаря, и маленький
список фамилий иначе «узнавал» бы почти любое слово.

## 11. Базовый словарь и его атрибуция

**Задача.** Получить общую морфологию русского языка (OpenCorpora, ~15 МБ),
не храня её в репозитории, и правильно указать атрибуцию (CC BY-SA 4.0) при
распространении.

**Как.** Три способа:
- CLI: `lexicon dicts fetch [--dicts DIR]` скачивает pymorphy2-dicts-ru,
  компилирует и записывает `base.opencorpora.dat` вместе с файлом `.meta`.
- Go: `basefetch.Fetch(dst)`. Только этот пакет тянет загрузчик pymorphy из
  gomorphy и логгер (zap); хосты, которые его не импортируют, их не
  компилируют.
- Встроить: положить байты `.dat` в `Options.Base`, а `.meta`, записанный
  `basefetch`, разобрать через `lexicon.ParseManifest` и передать в
  `Options.BaseManifest`. Словарь регистрируется как `base.builtin`; любой
  файл `base.*` в `Dir` его заменяет.

`Entry.Manifest` базового словаря содержит источник, версию, URL и
лицензию: показывайте их везде, где указываете атрибуцию данных. Сам
lexicon словарных данных не поставляет.

**Пример:** [base](../../examples/base/main.go),
`ExampleParseManifest`; CLI `dicts fetch`, `dicts list`.

**Доступно с:** 0.1.0.

## 12. Включать и выключать словари, перезагрузка без рестарта

**Задача.** Дать администратору отключить «шумный» словарь или подложить
новый список фамилий, пока сервис продолжает отвечать на запросы.

**Как.** `Registry.SetEnabled(ctx, name, on)` сохраняет состояние через
`Options.State` (`StateStore`, который хост реализует поверх своей БД; nil
— в памяти, всё включено) и подменяет снимок. `Registry.Reload(ctx)`
заново сканирует `Dir`, переоткрывает все словари и подменяет снимок.
Читатели никогда не блокируются: `Parse` фиксирует текущий снимок, а
старые словари закрываются, когда завершатся начатые вызовы.

Заменяйте файлы словарей атомарно — запишите временный файл и
переименуйте его поверх старого. `.dat` отображается в память:
перезапись на месте может обрушить идущие разборы.

**Пример:** [registry](../../examples/registry/main.go).

**Доступно с:** 0.1.0.

**Поведение в 0.1.0:** `Reload` переоткрывает все словари, даже если файл
не менялся (переиспользование по хэшу — открытый вопрос,
[todo](../todo.md)).

## 13. Понять, когда переиндексировать

**Задача.** Поисковый индекс хранит леммы, вычисленные какой-то версией
правил на каком-то наборе словарей. Нужно знать, когда они устарели.

**Как.** Храните `Analyzer.Version()` вместе с производными данными и
пересобирайте их при его изменении. Значение складывается из трёх частей:

| Часть | Меняется, когда | Пример значения |
|---|---|---|
| версия анализатора | правила анализа в библиотеке меняют термы | `analyzer-2` |
| `Rules.Name`-`Rules.Version` | таблица или правило орфографии меняет формы | `prereform-3` |
| `Registry.Version()` | словарь добавлен, удалён, включён, выключен или изменился его состав | хэш содержимого |

Профили — определения хоста и в неё не входят
([сценарий 6](#6-профиль-на-поле-против-омонимии)). Для сброса кэшей
словарных запросов достаточно одного `Registry.Version()`.

**Пример:** [registry](../../examples/registry/main.go),
`ExampleAnalyzer_Version`; CLI `analyze` печатает версию в stderr.

**Доступно с:** 0.1.0 (версия анализатора "2", `Modern` и `PreReform` —
"3").

**История:** каждая будущая запись с пометкой ⚠ переиндексация на этой
странице называет часть, которую она поднимает.

## 14. Проверить руками

**Задача.** Посмотреть, что lexicon делает с фразой, какие словари
загружены и откуда они, — без написания кода.

**Как.** `lexicon analyze [--dicts DIR] [--ortho modern|prereform]
[--profile SPEC] [--mode index|full] TEXT...` печатает по строке на терм:
исходный текст, форму, леммы с флагами; сводка по словарям и
`Analyzer.Version()` идут в stderr. `lexicon dicts list` печатает каждый
словарь с видом, форматом, состоянием, источником, хэшем, происхождением и
ошибкой. См. [cli.md](cli.md).

**Доступно с:** 0.1.0.
