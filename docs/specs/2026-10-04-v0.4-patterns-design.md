# lexicon v0.4 — patterns, person assembly, facts: design

Date: 2026-10-04. Status: approved by the owner section by section
(2026-10-04), pending review of this write-up.

This document amends the main design
([2026-09-24-lexicon-design.md](2026-09-24-lexicon-design.md), sections
"rules" → Pattern and "ner") and the earlier patterns plan
([plans/2026-09-24-v0.3-patterns.md](../plans/2026-09-24-v0.3-patterns.md),
decisions P1–P11). Where they differ, **this document wins**. The engine of
that plan (pattern model, compilation to a program, backtracking matcher,
activation by tags, facts) is kept; a new plan
(`plans/2026-10-04-v0.4-patterns.md`) replaces it for execution.

## Why the plan changes

genodex E9 (mention suggestions) needs a person's name assembled from
adjacent name words inside lexicon ([todo](../todo.md), owner decision
2026-10-04). The earlier plan cannot express it:

- a person is not one unit in the output;
- there is no selector for capitalisation, so an unknown capitalised word
  between name words cannot be picked up;
- an element has exactly one selector and there is no negation, so "a
  capitalised word that is not a given name" cannot be written;
- creating a span and retyping a span are one action (`Relabel`), which hides
  the difference between a relabelled dictionary span and a new one.

## Owner decisions (2026-10-04)

- **O1. Carrier: composite span.** A person reaches the host as a span of a
  host-chosen type (`person`) over the whole name, with the part spans
  (`given`, `patronymic`, `surname`) nested inside it. The type of a part is
  its role; each part keeps its `Refs`. Not a fact: relation facts must be
  able to point at a person by span index, golden sets score spans, and
  resolution keeps two persons from overlapping.
- **O2. Engine in lexicon, rules in the host.** lexicon ships the pattern
  engine and proves the person cases with a rule set in tests, golden
  fixtures and a runnable example. Real rule sets and type names stay host
  data, as the main design says.

## Design decisions

Numbering continues the plan's P-series.

### P12. Action `label` creates spans; `relabel` only retypes

Resolves Q-v03-5.

```go
type Label struct {
    Role   string  // a group role or a non-type element role
    Type   string
    Weight float32 // default 1
}
type Action struct { Relabel *Relabel; Boost *Boost; Label *Label; Emit *Emit }
```

- `label` creates a candidate of `Type` over the term range captured by
  `Role`. If a live candidate of `Type` already covers exactly that range, no
  duplicate is created: the existing one gets `+Weight` and context.
- The new candidate has no dictionary hits (`Refs` empty), origin "pattern"
  (scored with the trigger origin weight, P7), `+Weight`, context, and
  evidence `labelled by pattern <name>` (with `Explain`).
- It is flagged `Candidate` unless its range contains at least one candidate
  consumed by a `type` element of the same match. So an unknown word
  labelled `patronymic` is a `Candidate`; a `person` built over dictionary
  name spans is not.
- `Span.Normal` of a labelled span is built at output time, in text order:
  each span output nested inside it contributes its normal form (its first
  one when it has several), every other word its lemma, joined by spaces.
  Agreed normal forms stay with Q-v03-10.
- `relabel` now requires a role bound to a `type` element (P6 for span roles
  is unchanged: existing candidate of the target type wins with its refs,
  else retype in place as `Candidate`; the replaced reading is kept in
  `Alternatives`). P6's "relabel on a token role creates a span" moves to
  `label`.
- Compile errors: `label` on a role bound to a `type` element ("use
  relabel"); `relabel` on a role not bound to a `type` element ("use
  label"); unknown role; empty type.
- `Doc.Text[Span.Start:Span.End] == Span.Surface` holds for labelled spans.
- **Context for consumed parts (final review, 2026-10-04).** Every
  candidate the match consumed inside the labelled range gets context, in
  both cases (new candidate, existing candidate of the type): the match is
  the evidence for its parts. So a `RequiresContext` part («Мороз» in «Иван
  Мороз») survives `filterContext` and is output inside the person.
- **Flags of a composite (final review, 2026-10-04).** A labelled span with
  nested parts takes the per-word flags `Ambiguous` (ambiguous
  abbreviation) and `Predicted` only from positions not covered by any of
  its parts: a part settled its own words and carries their flags. `Abbrev`
  is still set for any covered abbreviation. A labelled span without parts
  keeps the per-word rule over its whole range. This settles the question
  raised during execution (Q-v04-1) and reverses the earlier ruling that a
  composite repeats the flags of all its words.

### P13. Composite spans and nesting

- The parts of a composite span appear in the output only when the host
  allows the nesting: `Config.Nesting{"person": {"given", "patronymic",
  "surname"}}` (CLI: `--nest 'person>given'` …). The default stays empty
  (Q-v02-7): without the pairs, resolution keeps either the whole or the
  parts. The documentation of `label` says so.
- A candidate of a type that may not nest inside the composite (a
  `settlement` reading of a surname) loses resolution there; after a
  `relabel` it is kept in the part's `Alternatives`.
- **Same-range nesting for labelled spans** (owner decision 2026-10-04). In
  v0.2 an inner span must be strictly shorter than the outer one. For an
  outer candidate created by `label` the inner span may cover the same
  range, when `Nesting` allows the pair. So a one-word person («ответчик
  Иванов», «крестьянин Сидоров», «восприемник Иван») is a `person` span
  over the name alone with its `surname` or `given` part nested on the same
  range; the defining word is context, not part of the range. Pairs of
  candidates that are not labelled keep the v0.2 rule, so existing hosts'
  nesting does not change.
  - Output order on one range: the outer span first, then the nested one.
  - The nested part is not an alternative of the outer span and never makes
    it `Ambiguous` (D7, D14 apply to candidates that compete, these do not).
  - Without the `Nesting` pair the two compete as before and the loser goes
    to `Alternatives`.
  - **A labelled inner created earlier (final review, 2026-10-04).** The
    same-range inner span may itself be labelled when it was created before
    the outer one (creation order of the candidates): «ответчик Лаптев»,
    where one pattern labels the unknown word `surname` and a later one
    labels the `person` over it. A same-range labelled inner is always
    older than its outer, so the chain of same-range nesting is finite.
  - **Alternatives and ties live on the part (final review, 2026-10-04).**
    A labelled winner that holds a part on its whole range gets no
    same-range alternatives and no tie flag; the other readings of the
    range (a `division` reading of the surname) compete with the part and
    are attached to it, with `Ambiguous` on an exact tie.
- A lone name word without a defining word stays a plain `given` or
  `surname` span: whether one word makes a person is the rule set's choice
  (a pattern with a context element), not the engine's.
- The estate, rank or party role of such a person is host data too: an
  `emit` with the person as argument, or a `label` of the word itself.
- `emit` arguments may name a role labelled or relabelled earlier in the
  same pattern, or a role bound to a `type` element (`type: person` in a
  later pattern). This is how «дочь X» gets the whole person as an argument.

### P14. Element conditions: `shape`, conjunction, `not`

Replaces P4's "exactly one selector per element"; resolves Q-v03-3.

```go
type Element struct {
    Type, Lemma, Grammeme, Token string   // alternatives with "|"
    Shape  Shape                          // rules.Shape: case, script
    Not    *Element                       // must not match here
    Any    bool
    Group  []Element
    Repeat Repeat
    Role   string
}
```

- `shape` is the existing `rules.Shape` (`case: lower|title|upper`,
  `script: cyrillic|latin`) as an element condition.
- Term conditions (`lemma`, `grammeme`, `token`, `shape`) on one element all
  have to hold for the term it consumes.
- Next to `type` they are checked on every word term of the consumed
  candidate: `{type: settlement, shape: {case: title}}` does not take
  «дер. Головина», a span that absorbed its keyword.
- `not` is a nested element with only `type`, `lemma`, `grammeme`, `token`,
  `shape`. It fails the outer element when it would match at the same
  position: `not: {type: given}` — no live candidate of type `given` starts
  at this term; term conditions inside `not` are negated as a whole. An
  element with only `not` consumes one term.
- Compile errors: an element with a `group` and any condition; `any` with
  other conditions; an empty element; `not` carrying `role`, `repeat`,
  `group`, `any` or `not`; unknown shape values (as for triggers).

### P15. Order of patterns; persons one per match

Resolves Q-v03-7: no priorities. Patterns apply in book order (P10), each on
the candidate state left by the previous one. A rule set puts fix-up
patterns first and assembly patterns after them.

Every person is one match of an assembly pattern; matches of one pattern do
not overlap (P3). Repeated role captures (Q-v03-8) and lazy quantifiers
(Q-v03-2) are not needed for persons and stay open for relation lists.

### P16. Span end over an abbreviation dot

A span whose last word is a dotted abbreviation ends after the dot
(«Калужской губ.», not «Калужской губ»). Applies to every output span; the
offsets contract is unchanged. A span also takes the dot when a span nested
directly inside it and ending at its last word takes it, so a nested span
never ends past its outer span. Golden sets are updated.

## The person rule set (tests, golden fixtures, example)

A host rule set; lexicon keeps this one as test data.

```yaml
sets:
  - name: persons
    patterns:
      # Fix-ups first.
      - name: given-as-patronymic        # «Алексей Степанов Сидоров»
        elements:
          - {type: given}
          - {type: given, role: p}
          - {type: surname}
        actions:
          - relabel: {role: p, type: patronymic}
      - name: place-as-surname           # «Анна Петрова Головина»
        elements:
          - {type: given}
          - {type: patronymic}
          - {type: settlement, shape: {case: title}, role: s}
        actions:
          - relabel: {role: s, type: surname}
      - name: unknown-patronymic         # «Анна Михаилова Кузнецова»
        elements:
          - {type: given}
          - {token: word, shape: {case: title}, not: {type: given|patronymic|surname}, role: p}
          - {type: surname}
        actions:
          - label: {role: p, type: patronymic}
      - name: unknown-surname
        elements:
          - {type: given}
          - {type: patronymic}
          - {token: word, shape: {case: title}, not: {type: given|patronymic|surname}, role: s}
        actions:
          - label: {role: s, type: surname}
      - name: unknown-surname-by-defining-word   # «ответчик Лаптев» (final review, 2026-10-04)
        elements:
          - {lemma: крестьянин|мещанин|ответчик|истец}
          - {token: word, shape: {case: title}, not: {type: given|patronymic|surname}, role: s}
        actions:
          - label: {role: s, type: surname}
      # Assembly.
      - name: person-surname-first       # «Кузнецова Анна Михайлова»
        elements:
          - group:
              - {type: surname}
              - {type: given}
              - {type: patronymic}
            role: who
        actions:
          - label: {role: who, type: person}
      - name: person                     # given + (patronymic | surname) + surname?
        elements:
          - group:
              - {type: given}
              - {type: patronymic|surname}
              - {type: surname, repeat: "?"}
            role: who
        actions:
          - label: {role: who, type: person}
      - name: person-by-defining-word    # «ответчик Иванов», «крестьянин Сидоров»
        elements:
          - {lemma: крестьянин|мещанин|ответчик|истец}
          - group:
              - {type: surname}
            role: who
        actions:
          - label: {role: who, type: person}
```

`person-by-defining-word` comes last: on «крестьянин Иван Сидоров» the word
after the keyword is a `given`, so it does not match, and `person` has
already taken the full name.

How the todo items are covered:

| Item | Mechanism |
|---|---|
| Person as one unit | `label … person` over a group; parts nested by `Config.Nesting` |
| Unknown word inside a name | `token` + `shape` + `not` element, `label` to a `Candidate` part |
| Surname that is also a place name | `relabel` settlement → surname after given + patronymic; settlement stays in `Alternatives` |
| Given-name reading in the patronymic slot | `relabel` given → patronymic; takes the patronymic record's refs when one covers the range |
| Several persons in one sentence | one match per person; `not: {type: given}` keeps an unknown-word slot from eating the next person's given name |
| One name word with a defining word (added 2026-10-04) | context element + one-element group, `label … person`; same-range nesting (P13) |

Guidance for rule authors (goes into the user documentation):

- An unknown-word slot stands only after a `given` element, never first in a
  pattern: the first word of a sentence is capitalised («Умер Иван Петров»).
- Assembly patterns contain no `any*`. The estate or period context comes
  from document tags (`when:`), not from a prefix such as `[estate] any*`.
- Whether a lone unknown word after a given name is a patronymic or a
  surname is a rule-set choice under tags (`period:pre1917` +
  `estate:peasant` → patronymic). The engine is neutral.

**Risk to settle by test.** Persons from different assembly patterns can
overlap («… Сидоров Анна Михайлова» also fits surname-first). Resolution
chooses by total value, and a candidate's value already includes its nested
selection (`resolver.schedule`), so the split into two full persons should
win on its own. A golden case «Иван Петров Сидоров Анна Михайлова Кузнецова»
must yield the two three-word persons. If it does not, the weight of a
labelled span grows with the number of spans it covers; this is decided in
the plan's pipeline task, before the golden task.

## Pipeline

```
matches → filterEarly → hints → triggers → PATTERNS → filterContext
        → scoring → resolution → output (+ dot rule P16) → facts
```

- Patterns run before `filterContext`: `relabel`, `boost` and `label` give
  context (P7) and keep `RequiresContext` entries alive.
- Patterns run per sentence over the candidate lattice (P1, P2); `ner`
  implements `rules.Lattice`.
- Facts are recorded while patterns apply and materialised after resolution
  and the `Types` filter; a fact with an argument that was not output is
  dropped; identical facts are de-duplicated (P8).
- **Facts follow a relabelled candidate (final review, 2026-10-04).** When
  a later `relabel` replaces a fact's argument with the existing candidate
  of the target type (P6), the fact points at that candidate, as it does
  when the argument is retyped in place.

## API (additions only)

- `rules`: `Pattern`, `Element`, `Repeat`, `Action`, `Relabel`, `Boost`,
  `Label`, `Emit`, `RuleSet.Patterns`, `Active.Patterns`, `Program`,
  `PatternMatch`, `Capture`, `LatticeSpan`, interface `Lattice` (in
  `rules/deps.go`).
- `ner`: `Fact{Kind string; Args map[string]int; Rule string}`,
  `Result.Facts`.
- `cmd/lexicon extract`: prints facts (table and JSONL).
- No new dependency. Rule files without `patterns` load as before.

## Versions

- `ner.extractorVersion`: `ner-2` → `ner-3`, once for the release. Patterns
  change nothing for books without patterns, but P16 changes span ends for
  every host: ⚠ re-extract.
- `analyzerVersion` and the `textnorm` rule versions do not change: no
  reindex.

## Scope of 0.4

In order of execution; the first three blocks unblock E9.

1. Engine: pattern model in rule files, compilation, matcher, activation by
   tags (plan tasks 1–3, with P14 elements).
2. Patterns in the pipeline: lattice, `relabel`, `boost`, `label` (P12),
   same-range nesting for labelled spans in the resolver (P13).
3. Golden cases for the five todo items, pre-reform and modern spelling,
   synthetic fixtures, with the person rule set above.
4. `emit` and `Result.Facts`: relations («сын/дочь X» with a person
   argument) and `age` («N лет»).
5. CLI `extract` prints facts.
6. Span end over an abbreviation dot (P16).
7. Benchmark with patterns; user documentation (EN + RU): scenarios for
   patterns, persons and facts, `library.md`, `cli.md`, runnable example
   `persons`, README, CHANGELOG.

Not in 0.4 (stay in `todo.md`): Q-v03-2 lazy quantifiers; Q-v03-8 repeated
role captures; Q-v03-4 facts in `nertest` golden sets (persons are scored as
spans); Q-v03-10 agreed normal forms.
